# 要件定義・設計・テストで決めることの線引き

要件定義では「**何を・どの条件で・何を満たせばよいか**」を決めます。「どう作るか」は設計工程、「どう確かめるか」はテスト工程で決めます。
この表は要件定義書の冒頭（「この要件定義書の範囲」）と、AIコーディングツール向けの `AGENTS.md` にも同じ内容で載ります（`packages/ai-core/src/boundary.ts`）。

| 区分 | 要件定義で決める（要件ナビで作る） | 設計工程で決める | テスト工程で決める |
| --- | --- | --- | --- |
| 業務 | 目的・範囲、利用者と役割、業務フロー（現状・見直し後）、**業務ルール**（計算・判定・制約・状態が変わる条件）と具体例 | 業務手順書の詳細 | 業務を通しで確かめる（受け入れテスト） |
| 機能・画面・帳票 | 機能要件（EARS）、画面一覧・画面遷移・**画面ごとの入出力項目**、**帳票・出力の一覧**、**まとめて行う処理（バッチ）の一覧** | 画面・帳票のレイアウト、文言・メッセージの文面、項目の表示形式、処理方式、ジョブの設計 | テストケースの詳細化、手順 |
| データ | エンティティ・データ項目・キー・必須・業務上の制約・区分値・**保存期間**、権限（CRUD） | 物理DB（テーブル・インデックス）、型と桁の確定、採番の方式 | テストデータ |
| 外部とのやり取り | 相手・方向・タイミング・受け渡すデータの概要、**つながらないときの業務上の扱い** | 項目の対応、形式・プロトコル、再送・タイムアウトの方式 | 外部と結合したテスト |
| 非機能 | 7分類26項目の水準と理由、確認方法 | 方式（冗長化・監視・暗号化・バックアップの実装） | 負荷・障害・セキュリティなどのテストの実施 |
| 品質・受け入れ | **受け入れ基準**（何を満たせば受け入れるか）、要件ごとのテストの観点 | エラーコードの体系 | テスト環境、不具合管理、テスト結果報告書、受け入れ基準に照らした判定の実施 |
| 管理 | **用語集**、**レビューと承認**、確定版と**差分**、変更要求と影響、未決事項 | 設計書の版管理 | テストの版管理 |

太字は、この線引きに合わせて追加したものです。

## 判断の目安

- **業務の担当者にしか決められないこと**は要件定義で決める（料金の計算、取り消せる期限、データを何年残すか、連携先が止まったら業務をどうするか、何を満たせば受け入れるか）
- **作り方によって変わること**は設計で決める（テーブルの分け方、API の形、画面の配置、メッセージの文面、再送の間隔）
- **確かめ方**はテストで決める（テストデータ、手順、環境）。ただし「何を確かめるか（観点）」と「何を満たせば合格か（受け入れ基準）」は要件定義で決める

## 要件ナビでの扱い

| 決めること | どこで作るか | 後工程への渡し方 |
| --- | --- | --- |
| 業務ルール | ヒアリングの「業務ルール」の段階（要件の区分 RL）。要件一覧で具体例を編集 | 具体例がそのままテストケース（`TC-RL-01-1` など）になる |
| 画面の入出力項目 | 「画面」で、採用した UML のデータ項目にひも付けて作る | 仕様書・開発用パッケージの「画面の入出力項目」。入力チェックはデータ項目定義の必須・業務上の制約・区分値 |
| 状態が変わる条件・保存期間・失敗時の扱い・帳票・バッチ | 「UML」の設計モデル | 仕様書・`get_design`・`requirements/design.md` |
| 用語集 | 要件一覧の「用語集」（AIの下書き＋編集） | 仕様書・`get_glossary`・`requirements/glossary.md`。要件文の表記ゆれを着手前チェックで知らせる |
| 受け入れ基準 | 「テスト・引き継ぎ」 | 仕様書・`get_acceptance`。報告されたテスト結果で判定する |
| レビューと承認 | 「変更管理」 | 承認が必要なプロジェクトは、いまの要件の内容で承認されるまで確定できない |
| 確定版の差分 | 「変更管理」 | `get_changes`・`GET /api/v1/projects/{id}/diff`。影響するテスト・ストーリー・画面つき |
