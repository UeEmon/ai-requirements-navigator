# 非機能要件シート

非機能要件（速さ・止まらなさ・情報の守り方・運用など）は、利用者との会話からは出てきにくく、稼働後に「遅い」「止まって困る」「個人情報が守られていない」と問題になりがちです。そこで「非機能要件」タブに、漏れなく検討するためのシートを用意しています。

考え方は IPA（情報処理推進機構）の「非機能要求グレード」を参考にしています（大項目ごとに段階的な水準から選ぶ、システムの重要度に応じた推奨水準を示す）。項目と水準の文言は、専門家でない人向けに本システムで独自に書いたものです。

## 流れ

1. **システムの性格に答える**（4つの質問）
   - 主に誰が使うか／止まるとどうなるか／どんな情報を扱うか／いつ使うか
   - 答えから重要度（社会的影響がほとんどない・限定される・極めて大きい）と、大項目ごとの推奨水準が決まります
2. **26項目を検討する**：項目ごとに、やさしい質問・なぜ決めるのか・段階的な水準（費用・手間への影響 ●○○○）・推奨が表示されます
   - 「この水準に決める」「対象外にする（理由が必要）」「保留にする（決める人を記録）」のどれかにします
   - 推奨より低い水準を選ぶときは理由を記録します（2段以上低いと、理由がない限り要対応）
3. **AIの提案を参考にする**：複数AIモードでは生成AIそれぞれが推奨水準を提案し、**意見が分かれた項目** と各AIの理由を並べて表示します。意見が一致した提案は、未検討の項目にまとめて採用できます（分かれた項目は人が決めます）。AIの理由は、別の水準に変えたときの理由としては引き継ぎません
4. **矛盾を確かめる**：項目どうしの矛盾をシステムが検出します（例）
   - 稼働率99.9%以上なのに、停止を自動で検知しない
   - 稼働率99.9%なのに、復旧は翌営業日まで
   - 1時間以内に復旧したいのに、バックアップは週1回
   - 個人情報を扱うのに、保存データを暗号化しない・操作の記録を残さない・個人情報保護法への対応がない
   - 社外の人が使うのに、ログインがIDとパスワードだけ
5. **要件にする**：決めた水準を EARS の非機能要件にします（例：「利用者が画面を操作したとき、予約システムは、操作の95%について3秒以内に結果を表示しなければならない。」）。水準を変えて作り直すと、要件も直します。体制・計画の取り決め（問い合わせ対応時間、切り替えの進め方）と「対策しない」水準は、要件にせずシートと仕様書に残します。要件定義の確定後は変更要求になります
6. **確定前の確認**：「要件定義を確定する」とき、未検討の項目や要対応の矛盾が残っていると確定を止め、内容を表示します。「非機能要件を検討する」か、理由を書いて確定するかを選びます（理由と、確認を省いたことは監査ログに残ります）

仕様書には「13. 非機能要件シート」として、重要度・検討済みの割合・要対応／確認の内容・全26項目の状態（決定した水準・推奨・理由）が入ります。

## 過大にしないための仕組み（適正化）

非機能要件は「念のため」「将来のため」で高くなりがちで、費用と期間を押し上げます。次の仕組みで、システムの規模と目的に見合う水準に近づけます。

1. **規模・目的・予算を聞く**：システムの性格の質問に「利用者（アカウント）の人数」「主な目的」「予算の規模感」を加えています
   - 予算が小さいときは、費用のかかる項目（性能・端末と法令などの環境・使いやすさ）の推奨を「中」までにします（情報の保護に関わる項目は下げません）
   - 長く使うだけでは「止まると困る」とは限らないため、利用時間だけで可用性の推奨を最上位にはしません（運用時間の推奨は「いつ使うか」の答えで決めます）
2. **似たシステムの事例と比べる**：答えが似た事例を最大3件選び、似ている度合い・費用と手間の目安を並べ、各項目の選択肢に「事例：〇〇」と表示します
   - **参考類型**（12件）：小規模店舗の予約受付、社内の申請・承認、中堅企業の販売・在庫管理、中規模のECサイト、自治体の住民向けオンライン申請、診療所の予約・問診、社内ポータル、物流倉庫の入出荷管理、会員制スクール、人事・給与、部署内の集計ツール、金融機関のオンラインサービス（最上位の参考）。よくあるシステムの一般的な水準の目安で、**特定の実在システムのデータではありません**
   - **社内の過去事例**：同じ組織の他のプロジェクトで6割以上決めた非機能要件シート
3. **過大の可能性を示す**
   - 推奨より高い水準：理由を記録するよう促します。2段以上高いのに理由がなければ「要対応」（確定前の確認で止まります）
   - 似た事例のどれよりも高い水準、全体の費用・手間の目安が事例の平均を2割以上上回るとき
   - 業務の実態に合わない水準：平日の業務時間だけ使うのに24時間365日の運用、止まっても手作業で代われるのに高い復旧・災害対策、社内の一部の人だけなのに最上位のアクセシビリティ、50人までなのに同時に1,000人の利用 など
4. **AIに見直してもらう**：決めた水準を、規模・目的・予算と似た事例に照らして見直させます。複数AIモードでは各AIの提案をまとめ、「AI 2/2 が『99.9%』への見直しを提案」のように票数と、下げた場合の影響を表示します。業務上の理由が書かれている項目は指摘しません。「この水準にする」で採用できます
5. 仕様書には、比べた事例と、このシステムと事例の費用・手間の目安を載せます

## 項目

| 大項目 | 項目 |
| --- | --- |
| 可用性 | 運用時間、稼働率、復旧までの時間（RTO）、データを戻せる時点（RPO）、大規模な災害への備え |
| 性能・拡張性 | 利用者数・同時に使う人数、画面の応答時間、利用が集中する時期、データ量の増え方、締め処理 |
| 運用・保守性 | バックアップ、監視と障害の知らせ、計画停止、問い合わせ対応の時間 |
| 移行性 | 今のデータの引き継ぎ、切り替えの進め方 |
| セキュリティ | 本人確認（ログイン）、権限、暗号化、操作の記録、脆弱性への対応 |
| システム環境 | 使う端末・ブラウザ、守るべき法令・基準、データを置く場所 |
| 使いやすさ | アクセシビリティ、使い始めるまでの手間 |

## API

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | `/api/projects/:id/nfr` | シート（項目・推奨・決定・AIの提案・評価） |
| PUT | `/api/projects/:id/nfr/profile` | システムの性格 `{ users, impact, data, hours }`（各0〜2） |
| PATCH | `/api/projects/:id/nfr/items/:key` | 項目の決定 `{ status: decided / na / deferred / undecided, level?, value?, rationale?, owner? }` |
| POST | `/api/projects/:id/nfr/suggest[?async=1]` | AIの提案（既定では未検討の項目だけ） |
| POST | `/api/projects/:id/nfr/apply-suggestions` | 意見が一致した提案を未検討の項目に採用 |
| GET | `/api/projects/:id/nfr/cases` | 比べる事例（参考類型と社内の過去事例） |
| POST | `/api/projects/:id/nfr/review[?async=1]` | AIによる適正化の見直し（過大な水準を下げる提案） |
| POST | `/api/projects/:id/nfr/requirements` | 決めた水準を EARS の非機能要件にする `{ systemName }` |
| POST | `/api/projects/:id/baseline` | 確定。未検討・要対応が残ると 409（`code: nfr_incomplete`）。`{ force: true, reason }` で理由を残して確定 |
