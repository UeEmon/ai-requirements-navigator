# ログインの設定

ログインの方法は3つから選びます（`AUTH_MODE`）。

| AUTH_MODE | 内容 | 向いている場面 |
| --- | --- | --- |
| `dev` | 開発用。パスワードなしで、組織と役割を画面右上で選ぶ（誰でも管理者を名乗れる） | 1台のPCでのお試しだけ |
| `local` | **要件ナビのログイン**。メールアドレスとパスワード。ほかに何も用意しなくてよい | 社内の小さなチーム・Cognito や Keycloak を用意しない場合 |
| `oidc` | Amazon Cognito・Keycloak など（OpenID Connect） | 会社のアカウントでログインしたい・AWS |

どの方法でも、どの組織に入れるか（ユーザー）と役割は、要件ナビの「組織」タブで管理者が決めます。**組織には管理者が1人以上必要** で、最後の管理者の役割を変えたり、外したりはできません。

## 要件ナビのログイン（AUTH_MODE=local）

```text
AUTH_MODE=local
# 任意
LOCAL_SESSION_HOURS=12          # ログインの有効時間
LOCAL_PASSWORD_MIN_LENGTH=10    # パスワードの最短の長さ
LOCAL_SETUP_TOKEN=              # 設定すると、初期設定にこの値が必要（公開した直後に他人に初期設定されないように）
```

1. **初期設定**: 利用者が1人もいないときに画面を開くと「初期設定」が出ます。組織の名前と、管理者（あなた）の名前・メールアドレス・パスワードを入れると、組織と管理者のアカウントができてログインします
2. **招待**: 管理者が「組織」タブの「ユーザーと役割」で、メールアドレスと役割を入れて招待します。パスワードを決める **一回限りのリンク**（7日間有効）が入った文が表示されるので、本人にメールやチャットで送ります（要件ナビからはメールを送りません）
3. 招待された人がリンクを開き、名前とパスワードを決めるとログインします。以後はメールアドレスとパスワードでログインします
4. すでにアカウントがある人（ほかの組織に入っている人）を招待した場合は、リンクは発行せず、いつものパスワードでログインして右上で組織を切り替えます

| 決まり | 内容 |
| --- | --- |
| パスワードの保存 | scrypt のハッシュだけを保存します。ログインの状態（トークン）とリンクも SHA-256 のハッシュだけを保存します |
| パスワードの決まり | 既定で10文字以上。メールアドレスと同じもの・同じ文字の繰り返しは使えません |
| 間違いが続いたとき | 5回続けて間違えると15分ログインできません。メールアドレスが登録されていないときも同じ答え・同じ時間で返します |
| パスワードを忘れたとき | 管理者が「パスワード再設定のリンク」（72時間有効・1回だけ）を発行します。再設定すると、ほかの端末でのログインは終わります |
| ほかの組織にも入っている人 | 管理者はパスワードを再設定できません（ほかの組織の管理者が知らないうちに変えられないように）。本人が右上の「アカウント」で変えます |
| 自分で変える | 右上の「アカウント」で表示名とパスワードを変えられます。パスワードを変えると、ほかの端末でのログインは終わります |
| 組織から外す | 外した人は、その組織に入れません。どの組織にも入っていなければログインできません |
| 2つ目の組織 | `BOOTSTRAP_TOKEN` を設定し、`POST /api/orgs` `{name, adminEmail}`（ヘッダー `x-bootstrap-token`）で作ります。最初の管理者のメールアドレスは必須で、アカウントがなければパスワードを決めるリンク（`adminSetupUrl`）を返します |
| 記録 | 初期設定・ログイン・リンクの発行・パスワードの変更と再設定は、監査ログに残ります（パスワードは記録しません） |

## 役割ごとにできること

役割（管理者・編集者・レビュー担当・閲覧者）ごとにできる操作は、「組織」タブの **「役割ごとにできること」** で確認できます。管理者は組織ごとに変えられます（変更は監査ログに残ります）。

| 操作（権限） | 既定で持つ役割 | 変えられるか |
| --- | --- | --- |
| プロジェクトの閲覧 | 全員 | 外せない |
| 出力・ダウンロード（仕様書・テスト・開発用パッケージ・課題のファイル） | 全員 | 変えられる |
| プロジェクトの作成（複製・書き出したファイルからの取り込みを含む） | 編集者以上 | 変えられる |
| 要件・設計の作成と編集（ヒアリング・AI・UML・画面・非機能要件・変更管理・レビューの依頼） | 編集者以上 | 変えられる |
| レビュー・承認 | レビュー担当以上 | 変えられる |
| 要件へのコメント（書く・解決済みにする） | レビュー担当以上 | 変えられる |
| 課題管理ツールへの登録 | 編集者以上 | 変えられる |
| プロジェクトの名前・AIの構成の変更 | 編集者以上 | 変えられる |
| プロジェクトの管理（アーカイブ・削除・承認の決まり・プロジェクトのメンバー） | 管理者 | 変えられる |
| AI設定・課題管理ツールとの連携・開発ツールとの連携・利用量・監査ログ | 管理者 | 変えられる |
| 組織設定の変更・ユーザーの管理 | 管理者 | **管理者だけ**（ほかの役割に渡せない） |

管理者は常にすべての操作ができます。API では `GET /api/orgs/{orgId}/permissions`（全員）・`PUT /api/orgs/{orgId}/permissions` `{roles: {editor: [...], reviewer: [...], viewer: [...]}}` または `{reset: true}`（管理者）。自分の権限は `GET /api/me` の `permissions` です。

役割の割り当てを変えた組織では、あとから足した権限（要件へのコメントなど）は、管理者が「役割ごとにできること」で入れるまで、管理者以外は持ちません。

## プロジェクトのメンバー

「プロジェクト設定」の一覧の **「メンバー」** で、プロジェクトの管理の権限を持つ人（既定は管理者）が、そのプロジェクトに入れる人を組織のメンバーから選べます（`GET/PUT /api/projects/{id}/members`）。

| 項目 | 内容 |
| --- | --- |
| メンバーに限る | チェックすると、選んだ人と組織の管理者だけが、このプロジェクトを見られます。入っていない人の一覧には出ず、開こうとしても「見つかりません」になります |
| このプロジェクトでの役割 | 編集者・レビュー担当・閲覧者から選びます。プロジェクトの中の操作は、組織での役割の代わりにこの役割で決まります（例：組織では編集者でも、このプロジェクトでは閲覧者）。役割ごとにできることは、組織の設定のとおりです |
| 組織の管理者 | メンバーに入れなくても、いつでも見られます（プロジェクトの役割にはできません） |
| 自分を外す | 管理者でない人が、自分を外して保存することはできません（開けなくなるため） |
| 記録 | 変更前後を監査ログ（`project.members`）に残します |

開発用ログイン（`AUTH_MODE=dev`）では利用者をメールアドレスで照合できないため、管理者以外はメンバーに限ったプロジェクトを開けません（API では `x-user-id` にメンバーのメールアドレスを入れると照合します）。外部連携のトークンは、今までどおりトークンで決めたプロジェクトに使えます。

## 組織設定

「組織」タブの「組織設定を編集する」で、管理者が次を変えられます（`PATCH /api/orgs/{orgId}`）。

| 項目 | 内容 |
| --- | --- |
| 組織の名前・説明 | 画面に表示します |
| 問い合わせ先のメールアドレス | 招待の文に入ります |
| 招待できるメールアドレスのドメイン | 決めると、ほかのドメインのメールアドレスは招待できません（すでにいるユーザーはそのまま） |
| AI の月間トークン上限 | 組織全体の上限（空なら上限なし） |

## ログイン画面（AUTH_MODE=oidc）

`AUTH_MODE=oidc` にすると、画面右上に「ログイン」ボタンが出ます。OpenID Connect の **認可コード＋PKCE** でログインし、コードとトークンの交換はサーバー（`/api/auth/token`）が行います。ブラウザからトークン窓口を直接呼ばないため、認証サーバー側の CORS 設定は不要です。

APIは **IDトークン** を検証します。

## 組織と役割（要件ナビで管理）

ログインの仕組み（Cognito・Keycloak）は **本人の確認だけ** に使います。どの組織に入れるか（メンバー）と役割は、要件ナビの **「組織」タブ** で、組織の管理者が決めます。

1. 組織を作る（初期セットアップ用トークン `BOOTSTRAP_TOKEN` と **最初の管理者のメールアドレス** を指定。画面右上の「組織を作成」または `POST /api/orgs` `{name, adminEmail}`）
2. 最初の管理者が、そのメールアドレスでログインする（アカウントがなければ、ログイン画面で作る）→ 管理者になる
3. 管理者が「組織」タブで、メンバーをメールアドレスで招待し、役割（管理者・編集者・レビュー担当・閲覧者）を選ぶ。表示される招待の文（ログインの URL 入り）を、メールやチャットで送る（要件ナビからはメールを送りません）
4. 招待された人が、同じメールアドレスでログインすると、その組織に入れる

| 決まり | 内容 |
| --- | --- |
| 招待との照合 | ログインの仕組みが **確認済み** としたメールアドレス（`email_verified`）と照合します。メールを送れないローカルの Keycloak では `OIDC_TRUST_UNVERIFIED_EMAIL=true` |
| 複数の組織 | 1人で複数の組織に入れます。画面右上で組織を切り替えます（API ではヘッダー `x-org-id`） |
| 外す | 外した人は、その組織に入れません（下のクレームがあっても入れません） |
| 管理者 | 組織の管理者は最低1人必要です。最後の管理者の役割を変えたり、外したりはできません |
| 招待できるドメイン | 組織設定で決めたドメインのメールアドレスだけを招待できます |
| 招待されていない人 | ログインはできても、どの組織にも入れません（「まだどの組織にも招待されていません」と表示） |
| 記録 | 招待・役割の変更・外したことは、監査ログに残ります |

### 以前の運用（クレームで組織と役割を決める）との互換

IDトークンに組織と役割のクレームがある利用者は、最初のログインで、その組織のメンバーとして登録します（役割はクレームのもの）。以後は「組織」タブの設定に従います（ログインの仕組み側で役割を変えても反映しません）。

| 項目 | 環境変数 | Cognito | Keycloak（同梱の設定） |
| --- | --- | --- | --- |
| 組織ID | `OIDC_ORG_CLAIM` | `custom:org_id`（カスタム属性） | `org_id`（ユーザー属性） |
| 権限 | `OIDC_ROLE_CLAIM` | `cognito:groups`（グループ） | `roles`（レルムロール） |

## AWS（Amazon Cognito）

`deploy/aws` の CDK が、ユーザープール・グループ・ログイン画面のドメイン・アプリクライアントを作ります。

```bash
cd deploy/aws
npx cdk deploy -c certificateArn=arn:aws:acm:ap-northeast-1:...:certificate/... -c domainName=req.example.com
```

- **HTTPS が必須です。** Cognito は https 以外の戻り先を受け付けないため、証明書（ACM）を指定してください。独自ドメインを使う場合は、DNS の CNAME を出力 `Url` の ALB に向けます
- ログイン画面のドメインは `arn-<アカウントID>.auth.<リージョン>.amazoncognito.com` です。変える場合は `-c cognitoDomainPrefix=...`
- 利用者は、ログイン画面の「サインアップ」で自分のアカウントを作れます（メールアドレスを確認）。組織に入れるかは、要件ナビの「組織」タブで管理者が招待して決めます
- 最初の組織は、出力 `BootstrapTokenSecret` のトークンと最初の管理者のメールアドレスで作ります（画面右上の「組織を作成」）
- Cognito の確認メールは、既定では送信数に上限があります（1日あたり）。多人数で使う場合は、Cognito のメール送信を Amazon SES にしてください
- 以前の運用（AWSコンソールでユーザーを作り、`custom:org_id` とグループを設定）も使えます。その人は最初のログインでメンバーとして登録されます

## ローカルDocker（Keycloak）

```bash
# .env に追記
AUTH_MODE=oidc
OIDC_ISSUER=http://localhost:8080/realms/arn
OIDC_DISCOVERY_URL=http://keycloak:8080/realms/arn/.well-known/openid-configuration
OIDC_CLIENT_ID=arn-web
OIDC_ORG_CLAIM=org_id
OIDC_ROLE_CLAIM=roles
BOOTSTRAP_TOKEN=任意の長い文字列

docker compose --profile oidc up --build
```

`deploy/keycloak/realm-arn.json` がレルム `arn`、クライアント `arn-web`（公開クライアント・PKCE必須）、ロール4種、クレームの設定を読み込みます。

`OIDC_DISCOVERY_URL` を分けているのは、ブラウザは `localhost:8080`、app コンテナは `keycloak:8080` で Keycloak に接続するためです（`KC_HOSTNAME_BACKCHANNEL_DYNAMIC`）。トークンの発行者はどちらも `http://localhost:8080/realms/arn` になります。

利用者は、ログイン画面の「Register」で自分のアカウントを作れます（同梱のレルムで有効）。ローカルの Keycloak はメールを送れないため、`.env` に `OIDC_TRUST_UNVERIFIED_EMAIL=true` を追加してください。組織に入れるかは、要件ナビの「組織」タブで管理者が招待して決めます。

管理画面（http://localhost:8080、admin / admin）で利用者を作る場合は、**Users** → **Add user**（メールアドレスを入れ、**Email verified** をオン）→ **Credentials** でパスワードを設定します。

## 動作の確認状況

- サーバー側（コード交換、更新、IDトークンの検証、招待との照合、組織・役割の判定、複数の組織の切り替え、監査ログへの記録）は、テスト用の認証サーバーを使った自動テストで確認しています
- Cognito・Keycloak との実際の接続と、ブラウザでのログイン画面の遷移は、この環境では確認できていません。導入時に一度確認してください
