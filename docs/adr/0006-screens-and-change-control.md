# ADR 0006: 画面は低精細に固定し、確定後の変更は影響分析を経て行う

- 状態: 決定
- 日付: 2026-10-02

## 背景

- 専門家でない利用者は、画面の見た目（色・配置・文言）に意見が集中しやすく、要件定義の時間を使い切ってしまうことがある
- 要件定義を確定した後の変更は、設計・画面・実装タスク・登録済みの課題に波及するが、その範囲が見えないまま変更されることが多い

## 決定

### 画面

- 画面モデルのスキーマに見た目の項目を持たせない（目的・使う人・要件・情報と操作・遷移のみ）
- プロトタイプは白黒のワイヤーフレームとし、スクリプトを使わない（画面の切り替えはラジオボタンとCSS）。埋め込み表示は `sandbox` の iframe、配信時も CSP で `sandbox` を付ける
- 画面への意見の振り分けはAIではなく **規則（語句の照合）** で行う。結果が毎回同じで、なぜそう判定したか（どの語句に反応したか）を説明できるため。両方を含む意見（mixed）は要件の部分を反映し、細部は申し送りにする
- 作り直しは3回目から、要件の確認に戻るよう促す（禁止はしない）

### 確定と変更管理

- 確定は「その時点の要件の写し」を確定版として保存する。確定後は要件の直接の編集・削除を API で拒否し（409）、ヒアリングの採用も変更要求に変える
- 影響分析は **トレース（確実）** と **AI（推測）** を分けて表示する。AIの指摘は実在する要件・画面・ストーリー・UML要素に限る。複数AIモードでは生成AIそれぞれの指摘に票数を付ける
- 判断の選択肢は「変更する／代替案で変更する／保留／変更しない」に固定し、それぞれの結果（版が上がる、見直しが必要なもの、工数の目安）を判断の前に示す
- 外部の課題管理ツールの課題は自動で更新しない（影響のある課題の一覧とリンクを示す）

## 理由

- 見た目を「表現できない」ようにするのが、注意を促すだけより確実
- 変更の可否は業務の判断であり、システムは判断材料（影響範囲・工数・リスク・代替案）をそろえる役割にとどめる
- 外部の課題を自動で書き換えると、開発チームの作業中の内容を壊すおそれがある
