# ADR 0012: プロジェクト単位のメンバー・要件へのコメント・複製と書き出し

- 状態: 決定
- 日付: 2026-10-10

## 背景

組織の役割（管理者・編集者・レビュー担当・閲覧者）だけでは、「この案件は関係者だけに見せたい」「組織では編集者だが、この案件では見るだけ」といった分け方ができなかった。また、レビューは承認・差し戻しの単位でしかやり取りできず、要件ごとの相談の場がなかった。要件は AI の案の採用からしか増やせず、プロジェクトを別の案件のたたき台にしたり、バックアップを取ったり、別の環境へ移したりする手段もなかった。

## 決定

- **プロジェクトのメンバーは、組織のメンバーから選ぶ。** メンバーに限る（`restricted`）と、選んだ人と組織の管理者だけが見られる。入っていない人には「見つかりません」と返し、あることも知らせない。権限の判定は `loadProject` の1か所に集め、プロジェクトの一覧・外部連携（ログインして使う場合）・非機能要件の事例の比較もそれに合わせる
- **プロジェクトでの役割は、組織での役割の代わりに使う**（上げることも下げることもできる）。プロジェクトの操作の権限は「プロジェクトでの役割」に、組織の操作の権限は「組織での役割」に従う。役割ごとの権限は組織の設定（役割ごとにできること）をそのまま使う。管理者はプロジェクトの役割にはせず、組織の管理者はいつでも見られる（締め出しを防ぐ）。管理者でない人が自分を外す保存は止める
- メンバーを決めるのは「プロジェクトの管理」の権限（既定は管理者）。変更前後を監査ログに残す
- **要件へのコメントは、要件の内容とは別に持つ。** 確定後も書ける（要件を変えないため、変更要求は要らない）。本文は書いた本人だけが直せ、解決済みにするのはコメントの権限を持つ人なら誰でもできる。消せるのは本人とプロジェクトの管理者。監査ログには本文を残さず、長さだけを残す（個人の意見を含むため）。新しい権限「要件へのコメント」（既定はレビュー担当以上）を足す
- **要件の手入力は、確定前だけ。** 確定後は今までどおり変更要求（追加）から入れ、影響を確認する
- **複製と書き出しは、同じ形（`arn-project/1`）を使う。** 写すのは「今の内容」（要件・資料・用語集・受け入れ基準・非機能要件・コメント・UML）で、履歴（ヒアリング・確定版・レビュー・変更要求・テスト結果）は写さない。要件は番号と版をそのまま保ち、削除した番号も欠番として持つ（番号を再利用しない決まりを守るため）。採番は「区分ごとの最大の番号の次」に変えた
- 書き出しには API キー・利用者の ID・メンバーの設定を入れない。取り込み先の組織に元の AI がなければ、登録済みの AI を使う。画面とタスク分解は、同じサーバーの中の複製でだけ写す（ファイルから取り込むと、要件との対応を確かめられないため）

## 対象外

プロジェクトごとのメンバーの招待（組織に招待してから選ぶ）、コメントの通知（メール・Webhook）、コメントへの返信のスレッド、書き出しの暗号化。
