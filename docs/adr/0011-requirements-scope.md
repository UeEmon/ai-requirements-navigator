# ADR 0011: 要件定義で決めることを線引きし、業務ルールは要件として扱う

- 状態: 決定
- 日付: 2026-10-03

## 背景

成果物を点検すると、後工程で必要なもののうち、業務の担当者にしか決められないもの（業務ルール、保存期間、連携先が止まったときの扱い、受け入れ基準など）が残っていた。一方で、画面のレイアウトや物理DBのように設計工程で決めるべきものまで要件定義で作り込むと、確定していないことを決めたように見せてしまう。

## 決定

- 工程ごとに決めることを表にし（[phase-boundaries.md](../phase-boundaries.md)）、要件定義書の冒頭と AGENTS.md に載せる。AIコーディングツールには「要件定義で決まっている（変えない）」と「設計で決めてよい」を区別して伝える
- **業務ルールは要件の区分（RL）にする。** 番号・版・確定版・変更要求・影響分析・差分・テストの導出の仕組みをそのまま使えるため。業務ルールには種類（計算・判定・制約・状態が変わる条件）と具体例（条件 → 結果）を持たせ、具体例は2つ以上を求め、そのままテストケースにする。ヒアリングに「業務ルール」の段階を加える
- 状態が変わる条件・保存期間・外部とのやり取りが失敗したときの扱い・帳票・バッチは、設計モデル（UML）の項目として AI に作らせる。画面の要素は、採用した設計モデルのデータ項目に「エンティティ.項目」でひも付ける
- **用語集と受け入れ基準は、確定版に含めない補足（シート）にする。** 変更のたびに変更要求を通すほどではないが、監査ログに残す。受け入れ基準は、報告されたテスト結果で判定する（判定の実施はテスト工程）
- **レビューと承認は、要件の内容の指紋（要件IDと版の組）に結びつける。** 承認した後に要件が変わると承認は無効になる。依頼した人は承認できない。確定に承認を必須にするかはプロジェクトの決まりとし、管理者だけが変えられる。必須のときは理由を書いても確定できない（非機能要件の確認とは違う）
- **確定版の差分は、要件IDごとに文・補足・優先度・区分を比べ、版だけが上がっていれば「構造・具体例の変更」とする。** 影響するテスト・ストーリー・画面を一緒に出す
- 要件定義書の節の番号は、描くときに振り直す（モジュールごとの節の有無で番号が飛ばないように）

## 対象外

画面・帳票のレイアウト、メッセージの文面、物理DB、API仕様、外部連携の項目対応と再送の方式、テストデータ・手順・環境、不具合管理、テスト結果報告書。
