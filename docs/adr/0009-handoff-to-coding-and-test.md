# ADR 0009: コーディング・テスト工程への引き継ぎは、規則で作るテスト観点と設計の表で補う

- 状態: 決定
- 日付: 2026-10-03

## 背景

成果物（EARS の要件、非機能要件シート、UML、画面一覧、タスク分解、仕様書）を点検したところ、後工程で次の情報が足りなかった。

- コーディング：データ項目の定義（キー・必須・桁や形式・区分値）、権限表、外部とのやり取り、業務の言葉とコード上の名前の対応、未決事項の一覧、機械で読める形式での受け渡し
- テスト：要件ごとのテストケース（正常系・異常系）、非機能要件の確認方法、要件からテストへの追跡

## 決定

- **テストケースは AI ではなく規則で作る。** EARS の文型ごとに観点を決めておく（イベント → 起きたとき・起きないとき、状態 → 状態の内・外、望ましくない振る舞い → 異常の再現、オプション → 機能あり・なし、数値と単位 → 境界値）。同じ要件からは同じ ID・同じケースが出る。要件を直せば毎回作り直されるため、古くならない
- **非機能要件の確認方法は、シートの26項目ごとに固定で持つ**（負荷試験・復旧訓練・リストア試験・脆弱性診断など）。シートから作っていない非機能要件は文の言葉から推定し、推定であることを表示する。推定もできないものは「確認方法未定」として着手前チェックで示す
- **ストーリーの受け入れ条件は受け入れテストにする。** ストーリーが結びつくすべての要件から辿れるようにする
- **データ項目定義・権限表・外部とのやり取りは設計モデル（UML）に持たせる。** 新しい項目は省略できる形で追加し、古い設計モデルでも表を作れるようにする（足りない部分は着手前チェックで「作り直すと付きます」と示す）
- **着手前チェックは規則で点検し、判定（引き渡せる／確認事項を共有すれば着手できる／足りないものがある）と、直す画面を示す。** 確定版の作成は止めない（非機能要件シートの確認とは違い、助言にとどめる）
- **引き継ぎパッケージは1つの JSON にまとめる**（`format: "arn-handoff/1"`）。開発者のツールや AI コーディングツールに、そのまま渡せる形にする

## 対象外

物理 DB 設計（テーブル定義）、API の詳細仕様（OpenAPI）、画面のレイアウト、テストデータとテスト環境の詳細は、設計工程で決める。要件定義の段階で作り込むと、確定していないことを決めたように見せてしまうため。

## 理由

- テスト観点を AI に作らせると、実行のたびに変わり、要件を直したときの追従も保証できない。EARS で文型をそろえているので、規則で十分な観点が作れる
- 観点（何を確かめるか）までを要件定義で決め、具体的な値と手順はテスト設計に任せる。要件定義の段階で手順まで書くと、確定していない設計を前提にしてしまう
- 着手前チェックを確定の条件にすると、画面のないシステムや小さな改修で進められなくなる。足りないものと直す場所を見せるほうが、現場の判断に合う
